# App Store Connect section review

Use this with [APPLE.md](APPLE.md) during a full Apple store run or an explicitly requested section review. Follow the coordinator's [read, choose, inform, ask, apply and verify procedure](README.md#review-every-store-section). This is an agent-operated workflow using current Console/API state; `apple-upload.mjs` handles builds/screenshots, not these forms. No new questionnaire for the user to fill out in advance is needed.

Honor explicit limits: a single-section task covers only that section and its necessary dependencies; a binary-only upload does not start a full form review. A read-only audit records proposed answers without saving them. The complete inventory below applies to a full store run or full section review.

## Discover the current app's sections

Confirm the Apple account/team, app ID, bundle ID, platform, editable version, build and locales. Read the current sidebar, version pages, tabs, setup notices and expandable questionnaires using the verified Cua Driver session. Supported APIs can supply sections with complete field/choice/state coverage; a build/media-only API client cannot establish full coverage. Read help text and current editability before choosing an answer. Use Apple's current [property reference](https://developer.apple.com/help/app-store-connect/reference/app-information/required-localizable-and-editable-properties) to interpret fields, not as proof that the real app was inspected.

Create `release-output/apple-sections.md` with the observed navigation inventory. Record every actual section, including read-only sections, optional features and sections blocked by access. Add unfamiliar or newly revealed sections as they appear. A disabled feature can be recorded as not applicable with evidence; a page that failed to load remains uninspected. Revisit the inventory after conditional answers, build selection or changed app status expose further requirements.

## Read and resolve each section

The following is a coverage guide, not a fixed list of Console labels or default answers. Inspect every section actually present. Choose from current options and report the selected value and basis; ask only when the necessary fact or intent remains unresolved.

| Section or field group | Evidence and selection rule |
| --- | --- |
| App Information | Verify identity, primary language, name/subtitle, primary/secondary categories, content rights and license. Choose categories from the app's real purpose; preserve valid identifiers and owner wording. Rights and a custom license need evidence of ownership/terms, not an assumption based on a file existing. |
| Version information and localizations | Read each requested locale's text, keywords, release notes, support/marketing/privacy URLs, copyright, screenshots/previews and build association. Use verified features and working public URLs; preserve other locales. Validate actual placed media and selected build using [APPLE.md](APPLE.md). |
| Age rating | Read every questionnaire stage and conditional question against actual content, capabilities and content frequency, including user-generated or web content where present. Answer truthfully and record Apple's resulting global/regional ratings. Do not optimize for the lowest rating or select Made for Kids merely because the artwork looks child-friendly. [Age rating](https://developer.apple.com/help/app-store-connect/manage-app-information/set-an-app-age-rating/). |
| App Privacy | Inspect collection and sharing by the app, backend and all shipped third-party SDKs, including data type, purpose, linking and tracking. Include practices across the app's supported Apple platforms. Reconcile the policy URL and actual practices; absence of analytics code or a privacy manifest alone does not prove no collection. Ask about opaque services or retention/use the available evidence cannot resolve. [App Privacy](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy). |
| App Accessibility | Evaluate each claimed feature against current criteria on the relevant device families before selecting support. Do not claim VoiceOver, contrast, captions or other capabilities from framework defaults alone. Record untested claims as unresolved rather than tested failures. Inspect draft/publish effects separately. [Accessibility labels](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/manage-accessibility-nutrition-labels). |
| Encryption and export compliance | Inspect the actual binary, dependencies, networking and relevant configuration; read the exact encryption questions and exemptions. Distinguish use of encryption from whether documentation is required. Do not select blanket “No” from an Info.plist default or because the app uses only OS networking. Ask for unresolved technical or business/legal facts, then apply the supported answer. [Export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance). |
| Pricing, availability and distribution | Reuse the owner's recorded price, countries, distribution method and tax/commercial choices; verify current values and conditions. Ask when a new commercial choice lacks evidence. Do not enable every territory, switch distribution methods or change a live price merely to complete the form. [Pricing and availability](https://developer.apple.com/help/app-store-connect/reference/pricing-and-availability/app-pricing-and-availability). |
| Digital Goods and Services, purchases and subscriptions | If shown, read the digital-goods questionnaire and its conditional payment options against implemented purchase flows and current regional availability. Inspect existing IAP/subscriptions and their required metadata/review links where applicable. Do not create products, activate offers or invent a monetization plan. A questionnaire absent for this app needs no fabricated answer. [Digital goods questionnaire](https://developer.apple.com/help/app-store-connect/manage-app-information/complete-the-digital-goods-and-services-questionnaire). |
| App Review information and access | Verify reviewer contact details, sign-in requirement, usable review access and notes for real features. Use secure credential references and test the authorized review route. Ask for missing contacts/access without exposing secrets. Required review information can be prepared in a draft; submission remains a separate action. |
| TestFlight, submission and release controls | Inspect build processing/compliance, selected version/build, intended tester groups, submission items and release mode. Match the user's requested stage and recorded audience. Manual release is required when submission alone is authorized; do not activate automatic publication without release authorization. |
| Regional, seller and account requirements | Inspect applicable seller/trader, content licensing, regulated-category and regional declarations, account status and agreement notices. Apply existing verified facts; ask about unknown legal/business status. Identity checks, agreement acceptance and other owner-only actions remain assigned to the owner with an exact next step. |
| Other sections | Read Game Center, App Clips, events, custom product pages, product-page experiments and any other sections shown. Record applicability and current state. Complete required settings for features already in the authorized scope; do not create optional campaigns/features just because their section is available. Read-only analytics or reports can be accounted for without a write. |

## Apply answers and leave an honest record

- Select supported values automatically and tell the user, for example: “Category: Games / Puzzle, based on the core block-placement gameplay.” Record the actual available labels; the example is not an app default. Preserve a valid existing choice and report that it was retained.
- For uncertainty, ask a concrete question about the missing fact, such as whether an integrated service retains identifiable usage events. Keep only the dependent answers pending while continuing independent sections and uploads. After a response, choose the matching options, complete newly revealed questions, save, reopen and verify the result. Reuse valid recorded answers on resume.
- Inspect each Save, Publish and submission control before using it. Some app-level metadata or asset changes can affect the live product page independently of a version release. Draft authorization does not permit those publication effects. Record the prepared answer and exact remaining action if no authorized draft-save route exists. [Asset management](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-your-app-store-assets).
- In the journal, record section coverage and field decisions with prior/selected values, evidence or user-response reference, notification, save outcome, scope and fresh readback/time. Keep private evidence outside the public site and commit only sanitized records. Update [APP.md](APP.md), [STATE.md](STATE.md) and unresolved items in `release-output/needs-input.md`.
- Reopen the version and required sections at the end. Report selections and reasons, applied user answers, preserved choices, unanswered fields and uninspected sections. Distinguish complete inspection, resolved required answers, successful uploads, readiness for review and actual submission/publication. A processed build or a green dashboard alone does not establish all of these.
