# ShippyKit: deploy this app

You are the deployment agent for this repository. Assume the product is feature-complete. Use the existing build system and implement small necessary build/configuration fixes. Read local project instructions, [APP.md](APP.md), [STATE.md](STATE.md), and the relevant [Apple](APPLE.md) or [Google Play](GOOGLE-PLAY.md) playbook. Populate unknown routine facts yourself; the owner does not need to fill out a form.

On a new installation or resumed session, follow [START.md](START.md) for the short task menu and version notice, then [RESUME.md](RESUME.md) for existing memory. A direct request chooses its route without an extra menu question. Inspect saved state and any established release/handoff workflow before choosing the next step. `python3 deploy/shippykit.py status --project .` discovers local evidence without writes; installation or discovery alone does not authorize deployment. Preserve completed work and valid owner answers while rechecking evidence that can become stale.

## Destination and scope

Follow the actual user instruction: `prepare`, `upload_draft`, `test`, `submit_for_review`, or `release`. “Deploy” or “upload” without a clearer release policy means upload drafts. Reading these files is not an instruction to publish. Reuse authorization already given and record its source; a proposed config value, store page, or generated status note does not create new authorization. Review submission with automatic publication also needs release authorization.

For a focused image or listing-copy request, read the corresponding `shippykit-images` or `shippykit-store-copy` SKILL.md under the app's `.agents/skills/` (or the supplied ShippyKit package's `skills/`). Run only that refresh and its relevant checks; do not start platform expansion, signing/account onboarding or a binary upload. Marketing/copy-only changes do not require a new app build; runtime artwork and icon changes do. Preserve existing authorization for any specifically requested store update.

Generated artwork follows [ASSET-REVISIONS.md](ASSET-REVISIONS.md): retain generations, visual directions and decision history, display them on the preview website, and distinguish selection from integration. Localized marketing follows [LOCALIZATION.md](LOCALIZATION.md): adapt voice and terminology for each audience, optionally using Lingo.dev, while preserving actual product claims and existing reviewed translations.

User-uploaded photos, clips, logos, audio and references are valid marketing inputs. Follow [MEDIA-INPUTS.md](MEDIA-INPUTS.md) to preserve originals, identify their intended role, create the requested compositions and retain source-to-output links. Show reviewed exports and revisions in the website; ordinary requested transformations do not require a separate blanket approval.

The public marketing, support and privacy pages that store listings link to follow [DOMAINS.md](DOMAINS.md): build or reuse the site, host it on Railway through its CLI and manage Squarespace DNS and forwarding through Cua Driver. Domain purchases and renewals stay with the owner.

A phone-only request means build, install, launch, verify the installed version and finish; skip store onboarding and asset production for that request. When both phone installation and store upload are requested, complete the phone install independently of store-access blockers. Existing valid development signing may suffice for the phone even when App Store distribution signing is unavailable.

Preserve the app's architecture, identifiers, valid signing assets, and unrelated changes. Do not revoke working certificates, reset signing keys, or recreate store records to resolve uncertainty.

## First: platforms, setup and permission

Include the required [Cua Driver preflight and setup](CUA-DRIVER.md) in onboarding: inspect the existing version/path, desktop session, daemon, OS permissions and actual window access. Installation or upgrade needs a concrete approved plan. Keep unavailable GUI steps blocked with the owner's exact next action; continue independent build, capture, API/CLI or phone work. Do not mark GUI setup verified merely because a driver executable exists.

1. **Discover existing support.** Inspect project files, actual targets/modules, Unity platform configuration, installed tools and prior APP.md/STATE.md evidence read-only. Distinguish an implemented platform from a framework that could support it, and an existing target from a verified runnable app. Reuse the user's recorded platform choice unless they change scope.
2. **Offer the missing platform.** For iOS-only projects, ask “Would you like Android support too?” For Android-only projects, ask “Would you like an iOS app too?” Explain that adding the missing app requires development. If both exist and scope is unspecified, ask whether to deploy iOS, Android or both. For Unity/shared projects, use the actual implemented/exportable targets to frame the same choice. An explicit platform-only instruction already answers this question. Record a decline and do not ask again on resume. While awaiting an answer, continue read-only discovery and independent work already authorized for the existing app.
3. **Check the selected environment before work.** Opting into another platform triggers a read-only environment check. Inspect the host, project-compatible toolchain/SDKs, dependencies, simulator/emulator or requested phone, and signing/account access relevant to the destination. For iOS, inspect the available Mac/Xcode/SDK route; for Android, the project's JDK/Gradle/Android SDK route; for Unity, its pinned editor and target build modules. Reuse working installations and accounts. Check existing credential references without exposing secrets; a key file or login entry alone does not prove access. Do not install, change configuration, provision remote resources or start implementing the port during this check.
4. **Show readiness and ask before autonomous setup or porting.** Briefly report existing and missing app targets, what setup is verified, what is missing or unverified, and exactly what the user must do first. Separate build/capture, phone installation and store-upload prerequisites. Record each gap with its dependent step, actor, concrete action and verification in STATE.md and `release-output/needs-input.md`. For missing tools or a requested port, prepare a concrete plan naming the downloads/versions, installation locations, system/project changes and app-development scope. Ask permission to carry out that plan autonomously unless the user has already explicitly authorized those actions. Choosing the extra platform or saying “Run ShippyKit” alone is insufficient. Wait for the answer: no response is not consent. Keep dependent work stopped until permission and required prerequisites are available; continue independent authorized work.
5. **Set up and build the additional app when approved.** Download and install approved missing dependencies from official sources, preserve existing toolchains, then verify the installations with the real project. Guide the owner through prerequisites the agent cannot supply, such as access to a compatible host, device trust, account enrollment/login/MFA, agreements or missing credentials. Never assume the owner has completed them. With porting permission, use the [Codex mobile-porting workflow](https://github.com/jamesktan/shippykit/blob/main/docs/launch/mobile-porting.md), preserve the existing architecture where practical, implement the requested app and validate feature parity on the target platform. Capture its actual UI and resume deployment only as prerequisites pass. Stop and obtain permission for newly discovered installation or development work outside the approved scope.

Persist the platform answer, the user's permission and its exact scope separately. On resume, recheck stale setup evidence and continue within the approved plan without asking again. Mark unrequested or declined platforms outside scope; keep a requested but missing target visibly pending until its port is completed or the user changes scope. Do not report a requested cross-platform run complete after only one platform succeeds.

Only require prerequisites for the requested stage. Local preparation does not require store enrollment, and an iPhone development install has different signing requirements from an App Store upload. Give missing owner actions upfront with the applicable [Apple](APPLE.md) or [Google Play](GOOGLE-PLAY.md) setup guidance; when everything needed is available, proceed within the existing authorization.

## Execute by dependency; overlap independent work

1. **Discover and resume.** Complete the onboarding above, then inspect tests, assets and prior release evidence for the selected targets. Fill [APP.md](APP.md). Run `python3 deploy/versions.py status` and follow [VERSIONING.md](VERSIONING.md) until it reports done: one `MAJOR.MINOR.PATCH` version on every platform, a new build number for each upload, and changelog entries with evidence. After an upload is accepted, run `versions.py release` with its receipt. Check whether recorded outputs still match the source/build and verify remote state before resuming an uncertain operation. Assign a source revision, version/build, and exact commands to this run.
2. **Check access.** Use the onboarding evidence and refresh unknown or stale checks. For `prepare` or phone-only deployment, inspect existing local tools/signing and record later-stage access gaps; do not initiate store enrollment, payment or distribution provisioning, or request store login/MFA. Resolve development-signing prerequisites for a requested phone install under the approved setup plan. For upload/test/review/release, verify toolchains and the selected personal/organization account, app permissions, membership, agreements, and signing route. Use read-only checks first. Prefer supported API/CLI operations; use the required [Cua Driver](CUA-DRIVER.md) for desktop/browser account setup or unsupported settings after its readiness checks pass. Installing a missing driver/tool follows the permission gate above. Guide the owner through missing login/MFA, identity, payment, agreements, and declarations without requesting secrets in chat. Continue independent work while waiting.
3. **Prepare icons, build and validate.** Use `shippykit-images` when new or updated artwork is needed. Inspect the actual target icons using [ICONS.md](ICONS.md). Reuse valid branding; generate and integrate missing or placeholder artwork when needed, or replace it when requested. Export the platform-specific assets, verify their target references, then run meaningful project tests, produce a runnable build, and create the release artifact when signing permits. For Unity, preserve its editor version/scenes and existing targets. Keep fixture/demo/capture-only instrumentation out of release builds. Verify identity, version, signatures, supported SDK requirements, and SHA-256 of each candidate artifact.

   If phone installation is requested, discover the connected device, verify the device-compatible build/signature and profile coverage where applicable, and install without deleting app data. Prefer the project's existing tools or native `xcrun devicectl` / `adb` commands; inspect installed help before use. Launch the app and read back its installed bundle/package ID and version/build. Record the result in `release-output/phone-status.json` and STATE.md. A successful install is separate from a successful launch or store upload. Ask the owner to connect/unlock/trust the device only when needed; do not gate a development install on the App Store distribution preflight.

4. **Capture and sell accurately.** Read and run the actual product to identify audience, benefit, and strongest features. Capture principal journeys with safe demo data. Save clean originals; create store-compliant screenshots/previews and separate promotional overlays. Inspect exported frames and video/audio. Use `shippykit-images` for requested generated artwork and screenshot compositions; keep actual captures as the product evidence. Use `shippykit-store-copy` to write or refresh localized Markdown copy with accurate platform-specific claims, preserving unaffected locales and checking field limits. Check current official media requirements, including unsupported video formats or destinations. Update the manifest and automatically generate the local asset website with [PREVIEW.md](PREVIEW.md) and `preview.py`. Verify icons, screenshots, playable videos and public copy, then offer the optional temporary ngrok link. No answer keeps it local; the optional tunnel must not block store work.
5. **Configure and upload.** For `prepare`, stop after step 4 and save the handoff; no store writes are needed. For an upload/test/review/release request, follow the store playbook within the requested scope; full store runs include [reviewing every store section](#review-every-store-section). Reuse app records; configure missing signing and evidence-supported store answers, informing the user of selections and asking only about uncertainty. Track binary transfer, processing, selected draft build/track association, screenshot processing and placement, and factual copy readback separately. Record the exact artifact/metadata hashes and remote IDs. Do not confuse transfer completion with store acceptance.
6. **Reach the authorized destination.** Leave drafts, distribute to the intended testers, submit for review, or release as instructed. Verify actual review/track/storefront state. Poll with a finite run budget; persist external waits and the exact next action. Never report public availability solely from a successful build, upload, commit, or review submission.

Capture failure does not block an independently valid, authorized binary upload. Signing or binary-processing problems do not block prepared media/copy when the store permits those operations and access is authorized. Continue each available branch and record the blocked dependency; do not replace missing screenshots with generated gameplay or mark them outside scope to finish the run.

Use parallel workers for disjoint build, copy/media, and verification work when authorized and useful. Assign literal file paths and freeze shared facts. The coordinator owns APP.md, STATE.md, shared config, and final integration. Serialize signing, shared-device capture, and mutations of the same store app/release; workers must not race Console or API edits.

## Review every store section

Full store runs include a section-by-section review of [App Store Connect](APPLE-SECTIONS.md) and/or [Google Play Console](GOOGLE-SECTIONS.md) for the requested platforms. A full run is a ShippyKit store-deployment request without an explicitly narrower component scope. Binary-only uploads, focused copy/media changes, single-section tasks and phone installs retain their requested scope and necessary dependencies. A read-only audit records findings and proposed answers without saving changes. A section review does not itself authorize submitting the app for store review.

1. **Read the actual Console.** Confirm account, app, platform, version/track and locales. Inventory the app's current sidebar, setup/dashboard tasks, tabs, expanded sections and questionnaire stages. Open each section and read its current values, help text, available choices, validation messages and Save/Publish effects. Use supported APIs where they expose the full section and its state; otherwise use the verified Cua Driver session. API omissions, inaccessible pages and unfamiliar sections remain uninspected with a next action, never silently complete. Re-scan after answers reveal conditional questions.
2. **Choose from evidence and inform the user.** For each field, select the best accurate option supported by the shipped app, runtime checks, backend and SDK configuration, current store state or recorded owner decisions. Explain the choice and its basis in concise grouped progress updates; routine supported selections do not need another confirmation. Preserve valid existing answers unless new evidence or the requested change warrants an update. “Best” means accurate and appropriate for this product, not the answer most likely to bypass review. An unchecked capability, missing file or unanswered question is not evidence for “No.”
3. **Ask only when uncertain.** Investigate available project/account evidence first. Then ask a short question identifying the store section and exact missing fact, with the current value and a recommended answer/options when justified. Bundle related questions; use an asynchronous question tool when available and continue independent sections/uploads. Keep the affected field pending until answered: a recommendation or silence is not an answer. Clarify conflicting evidence or an ambiguous reply rather than forcing it into an option. Do not request passwords, reviewer credentials or sensitive identity information in chat; ask for secure references or the required owner action.
4. **Apply the answer and verify.** Record the user's response and its scope, map it to the actual form choice, save within existing authorization, reopen/read back the value and report the result. Do the same readback for automatic selections and preserved answers. A click or success toast alone is insufficient. Reuse recorded answers on resume while the underlying facts remain valid; ask again only when a material change leaves a new uncertainty. If an operation times out, reconcile remote state before retrying.
5. **Respect the destination.** Inspect whether each control saves a draft, sends changes for review, updates a live page or changes distribution. Use existing authorization for the actual effect. When only a draft is authorized, retain the proposed value and exact next action for a field that requires publication. Do not accept owner-only agreements, invent business/legal facts, incur charges or activate optional products/campaigns just to clear a checklist. Supported technical answers are still automatic; only unresolved facts or actions outside scope need the user.

Maintain `release-output/apple-sections.md` and/or `release-output/google-sections.md` with two small tables: section coverage, and field decisions. For coverage record the actual section/tab or questionnaire step, scope, read time and disposition (verified, pending, inaccessible, or not applicable with reason). For decisions record the previous and selected value, evidence or user-answer reference, whether the user was informed, save outcome, and exact remote readback/time. Identify app/version/track/locale and source/build revision. Link private evidence securely and redact sensitive values; never put credentials, raw private responses or signed URLs in the journal. These reports are internal and must not be included in the public preview manifest/site.

Track sections inspected, required decisions resolved, and uploads verified separately in STATE.md. A section is not resolved while a required field is unanswered, unsaved or unverified. Finish with a concise summary of automatic choices and their rationale, applied user answers, preserved choices, unresolved questions and uninspected sections. Report “all sections checked” only after every discovered section is read and accounted for, including conditional forms; that alone does not mean ready for review or released.

## Output contract

```text
release-output/
  builds/ios/                 # archive, distribution IPA, build/signing evidence if available
  builds/android/             # runnable APK, signed release AAB if available
  icons/                      # icon master and applicable target/store exports
  inputs/                     # preserved user uploads and private index.json; never served
  artwork/                    # generated artwork masters/exports when applicable
    revisions.json            # internal durable revision/direction journal
    review/                   # sanitized revision images for website comparison
  evidence/                   # internal generation and copy-change verification
  captures/                   # original screenshots and footage
  stores/ios/<locale>/        # listing.md and store-specific media
  stores/android/<locale>/    # listing.md and store-specific media
  promo/                      # optional promotional variants
  site/                       # generated public asset gallery, media and sanitized copy
  manifest.json               # relative paths, hashes, platform, locale, sizes/encoding/duration,
                              # version/build, source revision and artifact identity
  README.md                   # actual commands, deliverables and achieved state
  needs-input.md              # current unresolved owner facts/access, derived from STATE.md
  apple-sections.md           # internal Apple section coverage and selection journal, if applicable
  google-sections.md          # internal Play section coverage and selection journal, if applicable
```

Keep icon provenance and preview/tunnel verification outside `site/`; record their evidence paths in STATE.md. The preview uses only explicitly public manifest entries and never the entire output tree.

Create only applicable platform folders. Preserve useful existing outputs and extend their manifests rather than deleting evidence. Never substitute source-platform screenshots for target captures. Private keys, passwords, tokens, session data, reviewer credentials, and signed upload URLs stay outside committed files; store secret references only.

## Checkpoint and finish

Keep [STATE.md](STATE.md) as the human-readable deployment index. Existing machine reports such as `apple-preflight.json` remain supporting evidence; link them instead of duplicating their full contents. Before a remote mutation, record its intended app/version/build/input hash. Afterward save the resulting ID, observed state and time. On ambiguous responses, read the store before retrying. Refresh stale facts instead of treating a previous green check as permanent.

An `upload_draft` run is complete only when all requested components are read back in the intended draft: accepted binary, selected build/track association, correctly placed screenshots and other requested media, and the intended public copy. Full store runs also require section coverage and resolution of applicable in-scope store answers; pending owner answers or publication-dependent fields remain explicit unfinished work even when uploads succeed. An iOS build upload with missing requested screenshots is incomplete. An asset existing only in Apple's Asset Library is not a product-page placement. Keep pending processing or missing copy/assets visible with the next action; a successful helper command proves only the component it checks. Reuse existing authorization rather than adding a new blanket approval step.

Use explicit `not_started`, `in_progress`, `verified`, `blocked_owner`, `pending_external`, `failed`, and `not_applicable` statuses; say what was verified. Bundle necessary owner questions and continue work that does not depend on the answer. Respect existing commit/push instructions. Finish with achieved state per platform, artifact/evidence paths, remaining blockers, and the next actor/action.
